Điều kiện ban đầu

Ba người dùng A, B, C nhấn "Mua ngay" cùng lúc T=0ms. Kho chỉ còn 1 sản phẩm (available = on_hand − reserved = 1). Hệ thống phải đảm bảo đúng 1 đơn được xác nhận, 2 đơn còn lại bị hủy — không xảy ra oversell dù traffic burst đồng thời.

Từng bước chi tiết
T0
3 users đồng thời nhấn "Mua ngay"
API Gateway validate JWT, route đến Order Service. Order Service tạo 3 đơn độc lập trạng thái PENDING — không check tồn kho ngay tại bước này (tránh blocking, để Inventory Service xử lý async qua Kafka).
T1
3 events order.created lên Kafka
Order Service publish 3 events. Kafka đảm bảo delivery, Inventory Service consumer nhận và xử lý theo thứ tự. Dù 3 events đến gần như cùng lúc, consumer group serialize việc xử lý trong cùng partition.
A
User A — Lock acquired, reserve thành công
Inventory Service xử lý event của A đầu tiên:
// 1. Acquire Redis distributed lock SETNX lock:inventory:{skuId} "1" EX 10 → "OK" ← lock acquired thành công // 2. PostgreSQL pessimistic read SELECT * FROM inventory WHERE sku_id = ? FOR UPDATE; → on_hand=1, reserved=0, available=1 ≥ 1 ✓ // 3. Ghi nhận reserve & release lock UPDATE inventory SET quantity_reserved = 1; DEL lock:inventory:{skuId}; // 4. Emit success event → Kafka: inventory.reserved { orderId: A }
Order A → CONFIRMED  ·  Fulfillment Service tạo pick-pack task
B
User B — Hết hàng, đơn bị hủy
Inventory Service xử lý event của B ngay sau A:
// 1. Acquire lock (A đã release) SETNX lock:inventory:{skuId} "1" EX 10 → "OK" ← acquired // 2. DB check — A đã reserve rồi SELECT * FROM inventory FOR UPDATE; → on_hand=1, reserved=1, available=0 available(0) < requested(1) → INSUFFICIENT_STOCK // 3. Release lock, emit failure event DEL lock:inventory:{skuId}; → Kafka: inventory.reserve_failed { orderId: B }
Order B → CANCELLED  ·  Hoàn tiền nếu đã thanh toán
C
User C — Tương tự User B
available vẫn = 0. Emit inventory.reserve_failed, Order C → CANCELLED.
Cơ chế kỹ thuật
Redis Distributed Lock

SETNX (SET if Not eXists) + TTL 10s serialize access vào inventory. Nếu process crash, lock tự hết hạn — tránh deadlock. Chỉ 1 consumer xử lý 1 skuId tại một thời điểm.

Key: lock:inventory:{skuId} Value: "1" TTL: 10 giây (auto-expire) Cmd: SETNX = atomic SET if Not eXists
PostgreSQL Pessimistic Lock

SELECT ... FOR UPDATE lock dòng DB, ngăn concurrent read-modify-write. Kết hợp @Version (optimistic) cho bảo vệ 2 lớp.

@Lock(PESSIMISTIC_WRITE) @Query("SELECT i FROM Inventory i WHERE i.skuId = :skuId AND i.warehouse.id = :wId")
Kafka Choreography Saga

Mỗi service tự react với events — không cần central coordinator. Thất bại được bù trừ (compensating transaction) qua event reserve_failed.

inventory.reserved → Order: PENDING→CONFIRMED inventory.reserve_failed → Order: PENDING→CANCELLED → Refund triggered

Tính đúng đắn được bảo đảm

Redis SETNX serialize access → PostgreSQL FOR UPDATE bảo vệ data → Kafka saga bù trừ thất bại. Ba lớp phòng thủ này đảm bảo: dù N users cùng đặt hàng, chính xác min(N, available) đơn được confirm, không xảy ra oversell, không lost update, không race condition.
